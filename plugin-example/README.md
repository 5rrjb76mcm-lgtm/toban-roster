# 施設の部品（プラグイン）の作り方

公開版の `toban.html` に、施設だけの規則・暦・出力の様式・訳・プロファイルを足す仕組みです。
部品は施設の保存フォルダの `plugins/` に置くだけで読み込まれ（組み立て不要）、本体を更新しても施設の部品は残ります。1 ファイルで配りたいときは組み立て時に焼き込むこともできます。

このフォルダ（`plugin-example/`）がそのまま見本です。中身を自分の施設用に書き換えて、別の場所に置いて使ってください。

## フォルダの形

```
<施設の部品フォルダ>/
  rules/        規則の部品（*.js）        T.rules.register({...})
  calendars/    暦の部品（*.js）          T.calendars.register({...})
  docx/         勤務表 docx の様式（*.js） T.docx.register(id, render, { label })
  lang/         訳（*.json）              同じ code なら本体の表に重なる（自分の文面の英訳を足す）
  profiles/     施設プロファイル（*.json） 設定タブの「施設プロファイル」に並ぶ
```

サブフォルダはどれも任意です。知らない名前のサブフォルダは無視されます（組み立て時に知らせます）。

## 使い方（2 つの道。フォルダの形は同じ）

### A. 保存フォルダに置く（組み立て不要。ふだんはこちら）

```
勤務表/                 ← アプリの保存フォルダ（toban.html と同じ層）
  toban.html
  plugins/              ← この見本の中身をここに
    rules/  calendars/  docx/  lang/  profiles/
  202611/ 202612/ …
```

- 開始画面でこのフォルダに接続すると `plugins/` が自動で読み込まれ、規則の一覧・暦・様式・プロファイルに部品が並びます。見出しの版に `+plugins`、設定タブの「管理者向け」に読み込んだ一覧が出ます。
- ファイルを直したら、設定タブの管理者向け「保存フォルダの部品（plugins/）を読み直す」を押します（接続し直しても読み直します）。
- 読めなかったファイルは入力チェック（`施設の部品 … が読めません`）に出て、他の部分は動き続けます。
- 部品の規則で計算した月には使った部品の id が記録され、部品の無い環境で開くと入力チェックが知らせます（黙って違う勤務表になるのを防ぐ）。
- フォルダの JS はこのブラウザで実行されます。`toban.html` と同じ信頼の範囲（施設が自分のフォルダに置くもの）です。フォルダ接続なしの運用（ダウンロード保存）では読めないので、その場合は B を使います。

### B. 組み立て時に焼き込む（1 ファイルで配りたいとき）

```
cd toban-roster/webapp
../tools/.venv/bin/python build.py --plugins /path/to/<部品フォルダ> --out /path/to/toban.html
```

- `--plugins` は繰り返せます。取り込んだ一覧は見出しの版（`v2026.09.23 +<フォルダ名>`）と設定タブの管理者向けに出ます。
- 部品は本体の同じ種類のあとに読み込まれます（規則の部品は本体の規則の部品のあと。`needs` で本体の規則を参照できます）。
- 部品だけを試す: `node test_plugins_node.js [highs のパス]`（この見本を読み込んで確かめます。自分の部品を試すときは `PLUG` の場所を変えるか、同じ形の試験を書きます）。

## 0. 日ごとの区分（`T.dayFlags.register`）

規則の部品のファイルの中で `T.dayFlags.register({ id: "local.<施設>.<名前>", label: { ja: "学生実習", en: "Students" } })` と書くと、月別条件タブの「日ごとの区分・予定」の表に
その列（チェック欄）が出ます。月データには `day_flags = {日: [id]}` として入り、規則からは `P.dayHas(d, id)` / `P.daysWith(id)` で読めます。日ごとの予定の文は `P.dayNote(d)`。

## 0b. 職員別カレンダーの拡張（`T.calendarExt.register`）

同じく規則の部品のファイルの中で、職員別カレンダーの日ごとの欄を施設に合わせて変えられます。

```js
T.calendarExt.register({
  id: "local.<施設>.calendar",
  fixedTags: [{ label: "研修", shifts: ["day"] }, { label: "管理当直", shifts: ["day", "night"] }], // 固定欄の横に「印」の選択肢（month.fixed_tags に入る）
  fields: [{ id: "local.<施設>.pref", label: "希望の種類", options: [["a", "A"], ["b", "B"]] }],     // 日ごとの欄を足す（P.personDay(id, 氏名, 日) で読む）
  hideDuties: true,  // 午前・午後の業務の欄を隠す（定期業務のない施設）
  paidLeave: true,   // 不可の選択肢に「有給」を出す（本体の休みの日数の規則を使っていなくても）
  dayHead: true,     // 日付の見出しに日ごとの予定と区分（入力側ではチェックで付け外し）
  symbol(P, A, n, d) { return { t: "○", sup: "研" }; },  // 計算結果の記号（入力・結果の職員別カレンダーに出る）
  legend(P) { return [[{ t: "○" }, "日勤"]]; },
  when: R => T.ruleState(R, "local.<施設>.calendar") !== "off",  // 施設の設定（規則の状態）で付け外し
});
```

`T.dayFlags.register` にも `when(R)` を書けます（その区分を使う規則が「なし」なら表にも見出しにも出さない）。

## 0c. 月ごとの値の欄（規則の `ui.month`）

規則の部品に `ui: { month: { render(R, m), read(m, box) } }` を書くと、月別条件タブにその規則の欄（箱）が出ます。`render` は欄の HTML を返し（値は自分でエスケープする）、
`read` は欄の要素 `box` から値を読んで月データ `m` に書き戻します（保存される場所は `m.local_<施設>` のように部品ごとの名前で）。規則が「なし」のときは出ません。
独自の項目の名前は `local_<施設>`（または `local.<施設>`）で始めてください。保存状態・計算中の変更の判定では、この名前の項目だけ空値（null・[]・{}・""）も未指定と区別します（本体の欄は空欄と未指定を同じに扱う）。
別の PC の保存との統合（app の 3 者統合）では、本体が知らないトップレベルの項目は**値全体を 1 つの項目**として比べます（自分だけが変えた値は残り、両方が変えたら衝突として選べます。中の要素ごとの細かな統合はしません）。
日ごとのチェック欄で足りるなら 0. の `T.dayFlags.register` のほうが簡単です（月別条件タブの「日ごとの区分・予定」の表に列が増え、月データは `day_flags`）。

## 1. 規則の部品（`rules/*.js`）

本体の部品（`webapp/src/rules/*.js`）とまったく同じ形です。設計は `docs/rule-modules.md`、見本は [`rules/local.example.junior_no_friday_night.js`](rules/local.example.junior_no_friday_night.js)。

守ること:
- `id` は `local.<施設>.<名前>`（本体の id と重ならないように）。`api: 1`。
- **解く側（`solve`）・検算（`check`）・減点の数え直し（`penalty`）は別々に書く。** 1 つの式から作らない。試験（`test_penalty_node.js`）が両者の点数の一致を確かめます。
- 3 状態（必須／減点／なし）は `ctx.limit(id, 式, 向き, 右辺, {...})` を使うと、解く側・検算・減点の 3 か所で同じ書き方になります。
- `messages` の文面は `en` が必須（登録の検査で拒否されます）。日本語は `ja`。
- 画面の文面（`label`、`params` の `label`、`report` の `t("…")`）は日本語で書き、英訳は `lang/en.json` に足します（下記）。
- `fixtures` を書くと、減点の突き合わせ試験に自分の設定が加わります（`base` は `cardiology` か同梱のプロファイル id）。
- `python: false`（Python 版の参照実装はこの規則を知りません）。
- 共有用のプロファイル（設定タブの「プロファイルを書き出す」で名簿を含めないとき）は、名簿を役割と目安だけにし、氏名をキーにした項目（`R.local_<施設>.by_name[氏名]` など）と `name` が氏名の要素（`members: [{name, …}]`）を落とします。それ以外の形で個人の記録を持つなら、規則の定義に `share(R)` を書いて自分の項目から除いてください（書き出す複製 `R` を書き換える）。
- 規則の定義で使える追加の項目: `w0sub`（`sub` の重みの既定。プラグインの規則は同梱の重みの表に無いので自分で持つ）、`uses: ["quals"]`（ほかの規則が名簿に足す欄を使う。持ち主の規則が「なし」でも欄が出る）、`lookback(rules)`（前月末から取り込む日数）、`ui.month`（0c）。詳しくは `docs/rule-modules.md` §4。
- `fixtures` は、本体の減点の突き合わせ（`test_penalty_node.js`）をプラグインを読み込んだ状態で走らせたときにだけ使われます（本体の試験一式は保存フォルダのプラグインを読みません）。施設側で `T.plugins.load` してから同じ突き合わせを回す試験を用意してください。
- 本体の規則や施設の構成の値と**同じことを扱う**規則には `overlaps: ["<規則の id>"]`（両方とも使われていると設定画面と入力チェックで注意が出ます）や、
  `overlapsNote: "…"`（一覧に添える注意の文。数え方の違いなど）を書いておくと、あとで見る人が重なりに気づけます。
- 設定タブの規則の一覧と「使う規則」には、プラグインの規則に**出どころ**（読んだファイル名。組み立て時に取り込んだものは「（組み立て時）」）と「プラグイン」の印が付きます。規則の要約（説明資料の第 0 節）でも〔プラグイン〕と示します。
  別の出どころが先に定義していた id を登録し直すと、入力チェック（LINT_PLUGIN_OVERRIDE）で知らせます。

使える道具（抜粋。詳しくは `docs/rule-modules.md` §5）:
- 解く側 `ctx`: `names`（当番に入る人）、`slots`（枠 `[日, 勤務帯]`）、`work(s, n)`（勤務の変数）、`oc(s, n)`、`y(d, n)`（その日に勤務するか）、`busy(d, n)`、`total(n)`、`lp.add(式, "<=", 右辺)`、`lp.objAdd(重み, 変数)`、`limit(...)`、`P`（問題: `P.isRole(n, "junior")`, `P.dow(d)`（月曜が 0）, `P.isHoliday(d)`, `P.shiftLabel(k)` …）
- 検算・減点・入力チェック・説明資料の `ctx`: `worked(n, s)`, `onCall(n, s)`, `anyWork(n, d)`, `runs(n)`, `offDays(n)`, `viol(code, args, days, names)`, `add(weightKey, w, x)`, `push(code, args)`, `line(文)`, `lab(d)`, `t(...)`, `term(...)`, `limit(...)`

## 2. 暦の部品（`calendars/*.js`）

```js
T.calendars.register({ id: "us", label: { ja: "アメリカ合衆国の連邦祝日", en: "US federal holidays" }, holidays(y, m) { return [3]; } });
```

`holidays(y, m)` はその年月の祝日の日付（1〜末日）の並び。振替休日のような決まりも中で片付けます。施設の休日（毎年同じ月日）は部品でなくプロファイルの `calendar.closure` に書きます。見本: [`calendars/us.js`](calendars/us.js)。

## 3. docx の様式（`docx/*.js`）

```js
T.docx.register("day_list", (P, A, c) => "<w:p>…</w:p>", { label: "日ごとの一覧（A4縦）" });
```

`render(P, A, c)` が本文の XML を返します。`P` は問題、`A` は割当（`A.workers(s)`, `A.oc(s)`, `A.worked(n, s)`）、`c` は道具（`cell` / `row` / `table` / `para` / `sect` / `fillOf(d)` / `dateStamp()` / `label` / `changed(s, kind)` …。`webapp/src/docxgen.js` の `context`）。プロファイルの `docx.template` にその id を書くか、作成モードの「出力」で選びます。見本: [`docx/day_list.js`](docx/day_list.js)。

## 4. 訳（`lang/*.json`）

```json
{ "code": "en", "ui": { "補助の役割の人を金曜の夜勤に入れない（施設の部品の例）": "Keep {junior} staff off Friday nights" } }
```

`code` が本体にある言語（`en` など）なら、その表に**重なります**（本体の訳は残り、同じ鍵は部品が勝つ）。新しい言語を足すこともできます（`code`, `name`, `ui`, `msg`, `help`, `dow`, `list_sep` …。ひな形は `webapp/i18n_new.py`）。日本語は鍵そのものなので訳の表は要りません。

## 5. プロファイル（`profiles/*.json`）

設定タブの「プロファイルを書き出す」で作ったファイルをそのまま置きます。`profile.id` は他と重ならないように。見本: [`profiles/example-clinic.json`](profiles/example-clinic.json)（暦に上の `us` を指定しています。部品どうしは参照できます）。

## 部品の見え方と付け外し

- 部品由来の規則・日ごとの区分・月ごとの欄には、設定タブと月別条件タブで「部品」の印が付きます（印にカーソルを合わせると出どころのファイル名）。
- 設定タブ「施設の構成を作る」の **5b. 施設のプラグイン** に、読み込まれているプラグインがファイルごとに並びます（種類、保存フォルダから読んだもの／組み立て時に取り込んだもの、登録した規則・区分・拡張・様式・暦）。
  印を外すとそのファイルの規則は「なし」、日ごとの区分・カレンダーの拡張・様式・暦は無いものとして扱います（確認用。`rules.plugins_off` に残ります。訳とプロファイルは付け外しの対象外）。規則の状態は覚えているので、戻せば元どおりです。
- 画面では「プラグイン」と呼びます（この文書と設計文書では「施設の部品（プラグイン）」も同じ意味）。
- 読み込みの途中で失敗したファイルが触った登録（規則・区分・拡張・暦・様式）と、文面（規則の `messages`）・訳・プロファイルは、失敗した時点で読み込む前の状態に戻ります。
  登録済みの定義（ほかの規則の `messages` や訳の表など）をプラグインの中で直接書き換えることは想定していません。必ず登録口（`register` / `registerLang`）を通してください（切替で戻せるのは登録口を通した分だけです）。
- 名簿の読み戻しは前の職員の値を土台にするので、プラグインを外した状態で名簿を保存しても、そのプラグインが名簿に足した属性（`field`）は未知の値として残ります（欄を出しているときに空にした属性だけ消えます）。フォルダを切り替えると、前のフォルダで読んだ分はすべて外れ（同梱の定義を上書きしていたものは元に戻り）、保存データがその規則を参照していれば入力チェック（LINT_PLUGIN_MISSING）が知らせます。
- 組み立て時に取り込んだ部品にも同じ出どころ（`種類/ファイル名`）が付くので、保存フォルダの部品と同じように見えます。

## 公開との切り分け

- 施設の部品フォルダは公開リポジトリの**外**（施設の保存フォルダの `plugins/`）に置きます（実名や施設固有の運用が公開物に混ざらないように）。
- 本体（`toban.html`）を更新しても `plugins/` はそのまま効きます。組み立て時に焼き込んだ場合は同じ `--plugins` で組み立て直します。
- 汎用性のある部品は、上流（このリポジトリ）に依頼して本体の部品に取り込めます。そのとき id は `local.<施設>.…` から本体の名前に変わり、旧 id は `aliases` で読めるようにします。本体側の部品の形（`api`）が変わるときは `docs/rule-modules.md` と更新履歴に書きます。
- 多くの施設は部品を書かずに、施設プロファイル（作成モードで作れる）だけで足ります。部品が要るのは「本体の規則の値では表せない」規則・暦・様式だけです。

# 規則の部品化（ルールモジュール）の設計

- 状態（2026-09-22 時点の記録。以後の登録の形は §4 以降が正。2026-09-25 に出発点の科だけが使う 4 部品（カテ室の必要人数・副担当担当の平日夜勤回避・休日の役割の組合せ 2 件）を本体から外し、その施設のプラグイン（非公開）へ移した。見本データと試験はその規則を使わない）: 段階 0〜4 まで実装済み。`src/rules/` に 35 部品（2026-09-25 時点）。規則の一覧（`RULE_DEFS`）のうち部品でないのはオンコール（`oncall`）だけで、これは本体に残す（第 3 節）。名簿の欄（`columns`）・説明資料の第 9 節（`report`）・規則ごとの入力チェック（`lint`）・設定欄のボタン（`ui.acts`）も部品が持つ。本体に残るものは第 8.1 節。
- 対象: `webapp/src` の規則（`RULE_DEFS` の規則（2026-09-25 時点で 35＋オンコール））を、1 規則 1 部品にまとめる作り替え。
- この文書は `generalization-policy.md` §6.2 のモジュール登録の素案（`T.modules.register`）を置き換える。素案は減点の数え直し（`penalty`）、規則の 3 状態（必須／減点／なし）、作成モードより前に書いたもので、いまの実装と合わない。

## 1. なぜ部品にするか（全員向け）

いまの規則は、1 つの規則が平均して 4〜6 か所に分かれている。

| 場所 | 中身 |
| --- | --- |
| `model.js` | 規則の一覧（`RULE_DEFS`）、値の読み取り、規則の要約の文（`rulesSummary` の分岐） |
| `solver.js` | 整数計画の制約と目的関数の項 |
| `check.js` | 必須条件の検算（`check`）、減点の数え直し（`penalty`）、入力チェック（`lint`） |
| `app-settings.js` | 規則ごとの設定欄（`ruleParams`）とその読み取り、名簿の欄 |
| `messages.js`、`lang/*.json` | 違反・入力チェックの文面、画面の文言の訳 |
| `app-solve.js` | 解なしの診断のときの直し方（規則ごとの分岐） |

規則を 1 つ足すたびに、これを全部揃えて直す。直し漏れは静かに起きる（2026-09-21 の 2 連休の式の誤りは、減点の突き合わせを入れて初めて見つかった）。

部品にすると、1 つの規則が 1 つのファイルにまとまり、登録の関数が「解く側・検算・減点が揃っていること」を強制する。登録された部品は、減点の突き合わせと総当たりの試験に自動で乗る。

## 2. 変えないこと（原則）

1. **二重実装は崩さない。** 1 つの式から解く側と検算の両方を自動で作ると、式の誤りが両方に同じ形で入り、突き合わせで見つからなくなる。部品は、解く側（`solve`）・検算（`check`）・減点の数え直し（`penalty`）を**別々に書く**。共通にするのは「必須／減点／なし」の分岐などの仕掛けだけで、規則の中身（何を数え、何と比べるか）は 3 回書く。
2. **検算は解く側を見ない。** `check` と `penalty` は、割当（`Asg`）と `Problem` だけを受け取る。LP の変数や式は渡さない。
3. **単一の HTML で配る。** 本体の部品は `build.py` が組み立て時に取り込む。施設の部品は保存フォルダの `plugins/` から実行時に読む（接続済みのフォルダなので `file://` の制限に当たらない。第 8 節）か、`--plugins` で焼き込む（`file://` で動かない、個人情報を扱う画面で他人のコードを動かすことになる）。
4. **設定と保存データの形は変えない。** 部品にしても `rules.json` と月データのキーは同じ。部品化は内部の作り替えで、利用者から見える変化は無い。
5. **Python 版は凍結のまま。** 部品化の対象外。Python 版は知らない規則を使う設定で止まる（いまと同じ）。

## 3. 本体に残すもの・部品にするもの

| 本体（部品にしない） | 部品にする |
| --- | --- |
| 暦・枠の組み立て（1 日の区分、計算で決める日、1 枠の人数の下限・上限） | `RULE_DEFS` にある規則すべて（人数の理想値 `count_target` も部品） |
| 勤務・待機の変数、1 枠の人数の制約、待機の構成（オンコールの人数の表） | |
| 不可・有給・固定指定・前月末の接続 | |
| 避けたい日の参照解、既存案からの変更（`base`）、採点（`pin`）、試験用の崩し（`jitter`） | |
| 検算の枠の充足・不可・固定との不一致・固定指定による許容の分類 | |

オンコール（`oncall`）は規則の一覧にあるが、**本体に残す**（段階 3 で決めた）。待機の変数・待機の人数の表・「オンコールを使わない施設では待機を置かない」の検算は枠の組み立てそのもので、
部品にすると規則を「なし」にしたとき（部品は呼ばれない）に構造の検算が抜ける。設定欄（待機の人数の表）は作成モードの手順 4 が `ruleParams` 経由で出す。減点 `missing_young_oc` も本体。

- `T.RULE_DEFS` は登録された部品の一覧（`T.rules.defs`）。`model.js` の一覧（`RULE_DEFS_INLINE`）が先に全規則を登録し、`rules/*.js` がその上に実装を重ねる。
  部品に移した規則は、`model.js` の一覧では `{ id, group }` だけの控えにする（一覧での位置＝設定タブの表の並びを決める）。`T.ruleState`・`P.state`・`P.softW` はそのまま使える。
- **2 つの順がある。** 設定タブの表の並びは `model.js` の一覧の位置、解く側・検算で呼ぶ順は `order`（第 6.3 節）。別のものなので混ぜない。
- `id` の接頭辞: 本体の部品は無印（いまの id のまま）。施設固有の部品は `local.<施設 id>.<名前>`（第 8 節）。
- `api` は部品と本体の約束の版。`ctx` の形や登録の引数を非互換に変えたときに上げる。

## 5. 共通の道具

### 5.1 解く側の道具 `SolveCtx`

`solve(ctx, prm)` が受け取る。いまの `buildLP` の局所変数を名前付きで渡すもの。

| 名前 | 中身 | いまの実装 |
| --- | --- | --- |
| `P`, `lp`, `LP`, `E`, `W` | 問題、LP、式の組み立て、重み | 同名 |
| `names`, `slots`, `key(s)`, `has(s)` | 当番に入る人、枠、枠のキー、その枠があるか（前月末を含む） | 同名 |
| `work(s, n)`, `oc(s, n)` | 当月の勤務・待機の変数（無い枠は 0） | `work[key+"|"+n]` |
| `Wv(s, n)`, `Ov(s, n)`, `Ev(s, n)` | 前月末は定数、当月は変数の勤務・待機・どちらか | 同名 |
| `total(n)` | 当月の勤務回数の式 | `total[n]` |
| `workday(d, n)` | その日の勤務の枠数の式（前月末を含む） | `workday` |
| `y(d, n)` | その日に勤務したか（0/1。要るときだけ作る） | `yOf` |
| `busy(d, n)` | 休みでない日か（明けを休みに数えない施設では明けも） | `busyOf` |
| `roleSum(s, ref)` | 枠の勤務者のうち、規則での役目が `ref` の人数の式 | `isI` / `isA` / `isY` |
| `fixedInvolved(days, n)` | その日・その人に固定指定が絡むか | `fxW` |
| `firstPrev` | 前月末の接続の最初の日（0 以下） | `firstPrev` |
| `relaxed(key)` | 診断でその規則を外しているか | `relax.has` |
| `provide(name, value)`, `use(name)` | 部品どうしの事実の受け渡し（第 5.3 節） | 無し（新設） |

**3 状態の仕掛け** `ctx.limit` … いまの `pairBy`・`le1`・「減点なら補助変数」の繰り返しを 1 つにする。

```js
// expr（式）sense rhs を、規則 id の状態に従って入れる
//   必須: 制約。ただし fixed が真なら、固定指定が絡むので減点付きで許す（重み fixed_conflict）
//   減点: 超過分の補助変数を作り、P.softW(id) を掛けて目的関数へ
//   なし: 何もしない
ctx.limit(id, expr, "<=", rhs, { fixed: false, ub: 10 });
```

規則の中身（何の式を何と比べるか）は部品が書き、状態による分岐は `limit` が受け持つ。

### 5.2 検算の道具 `CheckCtx`

`check(ctx, prm)` と `penalty(ctx, prm)` が受け取る。**LP には触れない。**

| 名前 | 中身 | いまの実装 |
| --- | --- | --- |
| `P`, `A`, `names`, `N`, `lab(d)`, `slab(s)` | 問題、割当、当番に入る人、月の日数、日付と枠の表示 | 同名 |
| `worked(n, s)`, `onCall(n, s)`, `engaged(n, s)` | その枠で勤務・待機・どちらかをしたか（前月末を含む） | `A.worked` など |
| `workday(n, d)`, `y(n, d)`, `busy(n, d)` | 勤務の枠数、勤務したか、休みでない日か | `workday` / `yOf` / `busyOf` |
| `runs(n)` | 勤務した日の並び（前月末から翌月 1 日まで） | `runsOf` |
| `offDays(n)` | 休みの日（明けの扱いを含む） | `offOf` |
| `roleCount(s, ref)` | 枠の勤務者のうち役目が `ref` の人数 | `isRoleAt` |
| `viol(code, args, days, names, fixed?)` | 必須条件の違反を 1 件積む。`fixed`（真偽）を渡せばそれが「固定指定により許容」の可否になる。省略時は本体が `days`・`names` と固定指定の集合（勤務・OC を含む）で判定 | `viol` |
| `add(weightKey, w, x)` | 減点を積む（`penalty` のとき） | `add` |
| `limit(id, value, sense, rhs, {fixed, code, args, days, names})` | 3 状態の仕掛け。`check` では必須の違反（`fixed` を渡せば許容の可否もそれに従う。解く側と同じ範囲）、`penalty` では減点の点になる | 新設 |
| `provide` / `use` | 事実の受け渡し | 新設 |
| `unN(n, d)`, `unO(n, d)` | 夜間の不可、日中の不可（`"allday"` / 半日） | `lint` 向け |
| `canWork(n, s)` | 不可と日中の業務（規則 `duty_conflicts` を使うときだけ）を見て、その枠に入れるか | `lint` 向け（`canWork`） |
| `fixedWork()` | 固定指定した勤務の日（人 → 日の並び。名簿の人で枠がある分だけ） | `lint` 向け |
| `push(code, args, hintArgs)` | 入力チェックの指摘を積む（`lint` のとき）。直し方は `messages` の `<code>_HINT` | `push` |

`SolveCtx.limit` と `CheckCtx.limit` は同じ引数の並びにする。部品を読むと、解く側と検算が同じことを言っているかが目で比べられる。ただし中身（式の組み立てと数の計算）は別々に書く（原則 1）。

### 5.3 規則どうしが共有する事実

| 事実 | 使う規則 | 置き場所 |
| --- | --- | --- |
| 勤務した日 `y`、休みでない日 `busy`、勤務の並び | 連勤の上限・下限、連日、休みの日数、2 連休、勤務の間隔 | 本体の道具（5.1・5.2） |
| 役割の人数 `roleSum` | 日勤と夜勤の組合せ、同日集約、オンコール | 本体の道具 |
| 固定指定が絡むか | 連日・同日 2 枠・翌月 1 日の接続 | 本体の道具 |
| **期間の担当**（日ごとの担当者、期間に担当したか、完全な土日の担当日数） | 期間責任者、週末の均等、連続する週末、週末担当の日勤、履歴込みの偏り、土日の分割 | 部品 `period_charge` が `provide("charge", …)` で出し、使う部品は `needs: ["period_charge"]` |

`needs` に書いた部品が「なし」のとき、使う側の部品も動かない（いまの `chargeOn` の分岐と同じ）。循環は登録時に拒否する。

### 5.4 名簿の欄

名簿の欄の出し分け（金曜夜勤・休日日勤の希望・翌日が平日の夜勤・専門業務・専門外来の候補・資格）は、欄を使う規則の部品が `columns` で持つ。
`氏名・役割・何年目・目安・当番に入るか` は本体の欄（何年目は構成の規則を使うとき、目安は回数の規則を使うときだけ出す）。

```js
columns: [{ key: "fri", order: 10, at: "duty", label: "金曜夜勤の最低回数（月）", when: R => …,
            render(d, R, h) { … },                 // 1 人分のセルの中身（HTML）。h は esc / tx / sel / term
            begin() { return {}; },                 // 人をまたぐ値の入れ物（規則の値が人→値の表のとき）
            read(td, d, R, acc, name) { … },        // 1 人分を読む。d は名簿の 1 行（人の項目ならここに書く）、acc は begin の入れ物
            end(R, acc) { R.friday_night_min = acc; },  // 読み終わったら規則の値へ
            rename(R, o, n) { … },                  // 改名に追随
            field: "cath" }]                        // 人の項目に書く欄は、欄を隠しているときも値を残すために項目名を書く
```

- `at` は本体のどの欄の後に置くか（`years` / `quota` / `duty`。省略は `duty`＝末尾）。`order` は同じ位置の中での並び。
- 欄が出るのは規則を使っているとき（`when` があればそれも真のとき）。隠れた欄の値は `columnsAll` で読み、`field` があれば前の値を残す。
- 画面側（`app-settings.js`）は `T.rules.columns(R)` で見出しとセルを並べ、読み取りは `begin → read（人ごと）→ end` の順に呼ぶ。

### 5.5 試験との約束

3 実装（解く側・検算・減点）の一致試験は、共通の `Problem` の読み取りや仕様の解釈を同じように間違えると通ってしまう。`test_spec_examples_node.js` は人が規則の文から決めた期待値を検算と減点に直接当てる正解例で、規則の意味を変えたときはここも直す（期待値の根拠は各例のコメント）。

- **減点の突き合わせ**（`test_penalty_node.js`）は、登録された部品の `fixtures` を順に使う。いまの 22 設定の手書きの一覧は、部品の `fixtures` と本体の見本（施設プロファイル）に分かれる。
- **点が付いたかの一覧**（どの設定でも 0 点の項）は部品ごとに出す。重みを持つ部品で 0 点のままの項があれば失敗にする（いまは一覧を出すだけ）。
- **総当たり**（`test_brute_node.js`）は、いまは固定の設定（`CASES`）を回す。部品の `fixtures` が加わるのは減点の突き合わせだけ（`windows` による自動参加は未実装）。
- **入力チェックの移し替え**は `lint_same_node.js <git の版>` で確かめる（見本の施設と、わざと矛盾を入れた月で、指摘の code・値・文面・直し方の集合が同じか。並びは比べない）。
- 入力チェックの `_HINT` の揃いは、本体と部品の両方の `push("LINT_…")` を走査する。
- **訳の網羅**は、部品の `label`・`messages`・`summary`・`params` の文言と、`report` が `t("…")` に渡す文面も対象にする（走査は `src/*.js` と `src/rules/*.js`。`T.t` / `t` / `tx` / `tv` の呼び出し）。

### 5.6 説明資料の行

説明資料の第 9 節（調整目標の達成状況）は、部品の `report(ctx, prm)` が `ctx.line(文)` で積んだ行を並べる。`ctx` は `CheckCtx`（mode `report`）で、
`t`（訳）・`term`（役割の呼び方の差し込み）・`sep`（区切り）・`opts`（避けたい日の参照解 `avoidRef` など）が使える。
呼ぶ順は解く順（`order`）ではなく一覧の順（設定タブに並ぶ順）。規則を「なし」にした部品は呼ばれない。「なし」でも情報として出したい行
（同じ曜日の超過、連勤の分布、休日の役割の組合せ）は `reportAlways: true` を付け、部品の中で規則の状態を見て出し分ける。
本体に残る行はオンコールの `missing_young_oc` だけ。
- 登録の検査（`build.py --check` と同じ段で走る）: `solve` があるのに `check` も `penalty` も無い部品、`weight` があるのに `penalty` が無い部品、`messages` の `en` が無い部品を拒否する。

### 5.7 入力チェック

入力チェック（`T.lint`）は本体と部品に分かれる。本体が見るのは名簿・不可・固定指定の形（枠があるか、名簿の人か、不可と重なるか）と待機（オンコール）の固定、
役割の一覧、プロファイルの取り違え、各枠に入れる人がいるか。規則ごとの矛盾（固定指定と連日・同日・目安、期間責任者、専門業務、日中の業務、
休みの日数からの人数の見積もり、連勤の設定）は、その規則の部品の `lint(ctx, prm)` が `ctx.push` で積む。
規則を「なし」にした部品の入力チェックは出ない。必須のときだけ意味のあるものは部品の中で `P.isHard(id)` を見る（減点なら解けるので指摘しない）。
勤務日の見積もり（休みの日数の部品が出す事実 `busy_days`）は、構成の部品の入力チェックが `ctx.facts` にあるときだけ使う（`needs` にはしない。
`needs` は解く側も止めるため）。

## 6. 組み立てと呼ぶ順

### 6.1 ファイル

```
webapp/src/rules/
  same_weekday_cap.js
  friday_night_min.js
  …
webapp/src/rules-core.js       ← T.rules.register、SolveCtx / CheckCtx、limit
```

`build.py` は `src/rules-core.js` の後に `src/rules/*.js` を `order` の順で取り込む。`build.py --check` の相互参照の検査は、部品が `T.rules.register` 以外の名前を外に出さないことも見る。

### 6.2 1 回の計算の流れ

1. `new Problem(rules, month)`: 本体の読み取り → 各部品の `read(P, rules)` で `P.prm[id]` を作る。
2. `buildLP`: 本体の変数と枠の制約 → `SolveCtx` を作る → 状態が「なし」でない部品の `solve` を `order` の順に呼ぶ。
3. `check`: 本体の検算 → 部品の `check` を順に → 固定指定による許容の分類（本体）。
4. `penalty`: 本体の項（既存案からの変更など）→ 部品の `penalty` を順に。
5. `lint`、`rulesSummary`、設定画面、診断: 部品の `lint`・`summary`・`params`/`ui`・`diagnoseHint` を順に。

### 6.3 呼ぶ順 `order`

移す途中で、**移す前と後で解く側に渡す式が変わらない**ことを確かめる（第 7 節）。そのために、`order` はいまの `buildLP` の中の順に合わせて振る（100 刻み。間に足せるように）。補助変数の名前は通し番号（`lp.n`）で付くので、順が変わると LP の文字列が変わるためである。

口（`T.rules.runSolve(ctx, upto)` など）は複数置ける。`upto` 以下の順の部品をそこで動かし、動かした部品は覚えて二度呼ばない。
解く側の口は、移す前に規則があった位置に `upto` を指定して置く（150 人数の理想値、560 同じ曜日・金曜夜勤、810 回数の偏り・構成、930 当番に入る人数・希望・翌日が平日の夜勤、
950 夜勤翌日の業務、980 待機の偏り、末尾に残り）。道具の**定義**（`total`・`workday`・`firstPrev`・`fxW`・`yOf`・`busyOf`）は最初の口より前、枠の制約より前に置いてある
（定義だけでは LP は変わらない。使う部品が呼んだときに初めて変数ができる）。
検算の口は `upto` の代わりに id の配列も受け取る（`runCheck(cctx, ["composition"])`）。違反の並びを移す前と同じに保つためで、検算では順より並びが見える。
減点は合計なので、末尾の 1 つの口で全部を動かす。
人数の理想値（count_target）だけは、移す前は枠の制約の中で枠ごとに補助変数を作っていたので、移すと補助変数の並びが変わり LP の文字列が変わる（`lp_same_node.js` で nurse-2shift だけ DIFF）。
その部品は「崩した割当を固定して解いた点数と減点の数え直しが、移す前後で一致する」ことで確かめた（3 通りの割当で一致）。

## 7. 移し方

一度に移さず、1 部品ずつ移して、そのたびに次の 3 つを確かめる。

1. **LP が同じ**: `node webapp/lp_same_node.js [git の版]` が、見本の施設と規則の状態を変えた 8 設定で、その版と いまの `src` の `buildLP(P).lp.toLP()` を 3 段で比べる。
   (a) 文字列が同じ、(b) 制約の並びと補助変数の名前をそろえると同じ（部品に移すと人ごと・枠ごとの並びが変わるので、段階 2 からは多くがこれ）、
   (c) 制約の集合が違うとき: 移す前の版で解いた割当と崩した割当 2 つを、両方の版で全枠固定して解いた点数と減点の数え直しが一致する（`limit` の減点の式は `v ≥ expr − rhs` の形なので、
   移す前の `expr − 1 ≤ v` とは文字列が違うが同値）。(c) でも点数が違えば失敗。
2. **試験一式が通る**: golden（結果が基準と同じ）・回帰・減点の突き合わせ・総当たり・Python 版との突き合わせ。
3. **画面が同じ**: 設定タブの規則の表と要約の文が、移す前後で同じ。

| 段階 | 移す部品 | ねらい |
| --- | --- | --- |
| 0 | 登録の仕組み・`SolveCtx`・`CheckCtx`・`limit`。`RULE_DEFS` を登録から作る（中身は空の部品として全規則を登録）。**済** | 動きは何も変わらない |
| 1 | 他と絡まない規則: 同じ曜日の上限、金曜夜勤の最低回数、回数の偏り、人数の理想値、構成、当番に入る人数、当直希望、休日日勤の希望、偏り（待機）、翌日が平日の夜勤、夜勤翌日の業務。**済** | 部品の形を実際に使って確かめる |
| 2 | 共通の事実を使う規則: 連日、同日 2 枠、連勤の上限・下限、勤務帯のつながり、勤務の間隔、休みの日数、2 連休、週休日、隣接しない連日、OC を含む連続、勤務回数の範囲・目標。**済** | `y`・`busy`・`limit` の道具を固める |
| 3 | 絡みの多い規則: 期間責任者（`provide("charge")`）と週末の均等、日勤と夜勤の組合せ、同日集約、日中の専門業務、定期業務との両立、希望休の上限、避けたい日。オンコールは本体に残すと決めた。**済** | 事実の受け渡しを固める |
| 4 | 名簿の欄・設定欄の宣言化（`columns`・`params`）、説明資料の第 9 節を部品の `report` から作る。**済** | 画面側の分散をなくす |

段階ごとにコミットし、作業記録に「移した部品」「LP が同じだったか」を残す。

## 8. 施設固有の部品

- 施設にしか無い規則は、施設の部品フォルダの `rules/<名前>.js` に `T.rules.register({ id: "local.<施設 id>.<名前>", … })` で書く。形は本体の部品と同じで、同じ登録の検査と試験の約束（第 5.5 節）がかかる。
- 取り込む道は 2 つで、フォルダの形（種類ごとのサブフォルダ `rules/ calendars/ docx/ lang/ profiles/`）は同じ:
  (a) 実行時: 保存フォルダ（`toban.html` と同じ層）の `plugins/` を、フォルダに接続したときに `app-folder.js` が読んで `T.plugins.load(kind, name, text)`（`src/plugins.js`）に渡す。組み立て不要。
  読めなかった部品は `LINT_PLUGIN_ERROR`、部品の規則で計算した月（`month.plugins_used`）を部品なしで開くか、設定（`rules.rule_states`）で「なし」以外なのに登録の無い規則があると `LINT_PLUGIN_MISSING`。
  これらプラグインの有無の確認は `T.lintPlugins(P)` でも単独で得られる（`T.lint` の一部でもある）。計算の入口（app-solve.js）はまずこれで止め、次に `T.lint` を走らせる。`T.lint` が例外を出したら（プラグインの `lint` の不具合など）計算しない。
  実行時に読んだプラグインは読み込みの世代（`T.plugins.generation()`）と中身の印（`T.plugins.stamp()`）を持ち、計算中に読み直されていたら結果を採用しない。結果（`result.plugins`）と配布物の版の署名にも印が入る。
  計算中にフォルダへ接続したときのプラグインは、計算の後始末（`A.loadPendingPlugins`）で読み、読み終わるまで次の計算は始まらない。読み込んだ規則は既存の結果に入っていないので、再計算を促す。
  成功後の自動保存より前に保留分を読み切る。保存は勤務表・説明資料を出す前に、入力の読み取り／プラグインの欠落・読込失敗（`T.lintPlugins`）／計算後のプラグインの変化（`result.plugins` と `T.plugins.stamp()`。組み立て時に取り込んだプラグインは build.py が埋めた中身の印 `T.PLUGINS[].hash` で見る。印の無い旧形式の結果は通す）／検算（`T.check`。印の有無によらず必ず行い、違反か例外なら出さない）を順に確かめ、当たれば月データだけ保存して再計算を促す。結果には `result.build`（`T.BUILD_ID`）も記録する。保存は開始時の写し（月・設定・結果・年月・言語・接続の世代）から作り、月の切替・JSON の読込・言語の切替・プラグインの読み直し・画面からのフォルダの変更と再接続は `A.awaitSaves()` で進行中の保存を待ってから行う（保存中に月や接続先が替わっていたら、写しの月・フォルダにだけ書き、現在の保存基準は更新しない）。
  画面の側の約束は 2 か所にまとめてある。状態を切り替える操作（月・新しい月・サンプル・JSON の読込・フォルダの変更と再接続・表示言語・プラグインの読み直し）はすべて共通の窓口 `A.transition(kind, fn)`（app-core.js）を通す。窓口が「計算・診断中は断る」「進行中の保存を待つ」を担うので、新しい切替のボタンはこの窓口に処理を渡すだけでよい（保存の待ち行列の中からの接続は通さない）。フォルダへの保存は `A.prepareSave`（写しから出力を作る。state は読むだけ）→ `A.writeSave`（フォルダへ書く）→ `A.commitSave`（保存済みにする）の 3 段階で、`saveToFolderCore` はその並べ方だけを持つ（app-folder.js）。
  フォルダを替えると（`T.plugins.beginFolder`）、前のフォルダで実行時に読んだ登録（規則・区分・拡張・暦・様式・文面・訳・プロファイル）はすべて最初の写しへ戻る。保存データが参照する規則が無ければ `LINT_PLUGIN_MISSING` が知らせる（`LINT_PLUGIN_STALE` は互換のため残してあるが、いまは出ない）。
  部品が同梱の id（`jp`・`week_block` など）を上書きしていた場合は、そのフォルダの間だけ上書きが効き、フォルダを替えると同梱の定義に戻る。
  読み込みの途中で失敗した部品が新しく登録した暦・様式はその場で外す（半分だけ読めた部品を黙って使わない）。
  (b) 組み立て時: `build.py --plugins <フォルダ>`（繰り返し可）。本体の同じ種類のあとに焼き込み、一覧は `T.PLUGINS`。1 ファイルで配りたいとき用。
  作り方と見本は `plugin-example/README.md`（規則・暦・docx の様式・訳・プロファイルの 5 種類）。試験は `test_plugins_node.js`。
- まず本体の規則の値（構成の規則、効く日、対象外の資格など）で表せないかを考え、表せないときだけ施設固有の部品にする。値で表せる形に広げたほうがよいものは、本体の部品として足す。

## 8.1 段階 1〜4 で本体に残したもの

- 名簿の本体の欄（氏名・役割・何年目・目安・当番）と、改名時の月データの追随。部品の欄は `columns`（段階 4 で移した）。
- 入力チェックのうち名簿・不可・固定指定の形・待機の固定・役割の一覧・各枠に入れる人がいるか（第 5.7 節）。規則ごとの入力チェックは段階 4 の後に部品へ移した。
  移すときに規則の状態に従うようにした 3 点: 金曜夜勤の名簿にない人の指定（`LINT_FRIDAY_MIN_NOT_CANDIDATE`）と固定指定が目安を超える指摘（`LINT_FIXED_OVER_QUOTA`）は
  その規則を使うときだけ、固定した夜勤・オンコールと日中の業務の重なり（`LINT_FIXED_NIGHT_NEXT_*`・`LINT_FIXED_OC_*_EXTERNAL`）は規則 `duty_conflicts` を使うときだけ出る
  （移す前はどれも規則の状態に関わらず出ていた）。
- 名簿・役割の追加・削除・並べ替えのボタンは本体。部品の設定欄のボタン（構成の表・勤務帯のつながりの表の行の追加・削除）は部品の `ui.acts` / `ui.act`。
- 説明資料の第 9 節のうち、オンコールの行（`missing_young_oc`）は本体（`report.js`）。ほかの節（違反の一覧・集計・専門業務の表・月末）も本体で、部品の `check` が積んだ違反と本体の道具（`T.cathTable`・`T.restDays`）から作る。
- 段階 2 で: 予備の役割の登用（月 1 回まで・`chief_duty`）は勤務回数の規則ではなく本体。翌月 1 日の固定指定のうち、期間責任者の月またぎの接続は本体（段階 3 の `period_charge` へ）。
  週休日の一覧（`T.restDays`）は説明資料も使うので本体に残し、部品の `check` が呼ぶ。
- 段階 2 で直した挙動: 翌月 1 日の固定指定との連日（`consecutive_days`）は、移す前は規則の状態を見ずに常に必須だった（連日を許す 2 交代の施設でも、翌月 1 日に固定があると月末の勤務が禁止された）。
  部品では規則の状態に従う（必須なら禁止、減点なら減点、使わないなら何もしない）。検算（`CONSECUTIVE_NEXT_MONTH`）はもともと必須のときだけだったので、これで解く側と検算がそろった。
- 段階 3 で: 期間責任者の部品が事実 `charge` を出す。解く側は `{cday, chargedP, fullDays}`（式）、検算は `{map}`（期間 → 日 → 担当者。本体が結果の表示に使う）、
  減点は `{cday, charged, fullDays}`（数）。週末の均等は `needs: ["period_charge"]` でこれを使う。
  専門業務の表（`T.cathTable`）・週休日の一覧（`T.restDays`）は説明資料も使うので本体に残し、部品の `check` が呼ぶ。
  避けたい日の参照解（`solveWithAvoidRef`）は本体で、部品は `ctx.opts`（`avoidRef` / `ignoreAvoid`）を見る。定期業務の診断の人ごとの外し（`duties:<氏名>`）は部品が `ctx.relaxed` で見る。
  `lp_same_node.js` の並びをそろえる処理に、目的関数の項の整列を足した（部品にすると項の入る順が変わる。段階 3 の 8 設定はすべて制約の集合が同じ）。
- 段階 4 で: 第 9 節の並びが変わった（移す前は手書きの順、いまは一覧の順）。同日 2 枠と連日の行は 1 行にまとめていたのを部品ごとの 2 行に分けた。
  規則を「なし」にした部品の行は出なくなった（移す前は当直希望・避けたい日・OC を含む連続などが規則の状態に関わらず出ていた）。
  `reportAlways` を付けた 3 部品（同じ曜日の上限・連勤の上限・日勤と夜勤の組合せ）だけは移す前と同じく常に出る。

## 9. 決めていないこと

- オンコールを部品にするか（待機の変数と構成の表が本体と一体。段階 3 で決める）。
- 部品の設定値を `rules` のどこに置くか。いまは規則ごとにばらばらのキー（`max_same_weekday_shifts`、`run_length.max`、`days_off.basis` など）。部品化の後で `rules.params[<id>]` に寄せるかは、保存データの移行と合わせて別に決める（原則 4 のため、部品化の間は動かさない）。
- 診断の細かさ（いまの「個人ごとに外して試す」絞り込み）を部品の側に持たせるか。

## 10. 暦の部品（祝日の出どころ）

規則の部品とは別の小さな登録口。祝日は国・地域ごとに違うので、日本の祝日を本体から `src/calendars/jp.js` に出し、施設が選ぶ形にした。

```js
T.calendars.register({ id: "jp", label: { ja: "日本の祝日", en: "Japanese public holidays" }, holidays(y, m) { return [3, 23]; } });
```

- `holidays(y, m)` はその年月の祝日の日付（1〜末日）の並びを返す。振替休日・国民の休日のような国ごとの決まりも部品の中で片付ける。
- `none`（祝日なし＝土日だけ）は本体が登録する。
- 施設の休日（年末年始のように毎年同じ月日の休み）は祝日ではないので、施設プロファイルの `profile.calendar.closure`（`[{ month, days }]`）に書く。
  `profile.calendar.holidays` が出どころの id。暦の指定が無い保存データは「日本の祝日＋12/29〜1/3」（移す前と同じ）。
- 本体の口: `T.calendarOf(rules)`（整えた暦）、`T.holidaysOf(rules, y, m)` → `{ holidays, closure }`（月の設定の `holidays` / `closure_days` に入れる形）、`T.isOffDay(rules, y, m, d)`。
  月を作るとき（`blankMonth` / 「暦から自動入力」）と翌月 1 日が休日かの判定が使う。計算は月の設定に写した日付だけを見るので、暦の部品は解く側・検算に触れない。
- 画面: 作成モードの第 2 段「暦（祝日と施設の休日）」で出どころを選び、施設の休日を「月/日」のカンマ区切りで書く。説明資料の「施設の構成」に暦の 1 行が出る。
- 「土日」の定義（金土が休みの地域など）は動かしていない。置き場は `profile.calendar.weekend` を予定しているが、`isWeekend` の使用箇所が多いので別の段階にする。
- 同梱のプロファイルは暦を明示する（試験が確かめる）。病棟の 2 交代は施設の休日なし、当直系は年末年始あり。
